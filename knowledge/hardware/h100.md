# NVIDIA H100 SXM (Hopper, sm_90a, compute capability 9.0): fact sheet

- 132 SMs; 4 warp schedulers and 4 tensor cores per SM; 32-thread warps; max 64 warps (2048 threads) and 32 blocks per SM.
- Registers: 64K x 32-bit per SM, max 255 per thread. A 128x128 WGMMA consumer kernel runs at low occupancy by design (~14-25%).
- Shared memory: 228 KB per SM (L1 + smem = 256 KB), up to 227 KB per block (opt in: `cudaFuncSetAttribute(f, cudaFuncAttributeMaxDynamicSharedMemorySize, n)`; >48 KB needs it).
- L2: 50 MB. HBM3: 80 GB at 3.35 TB/s. FP32 (non-tensor) ~67 TFLOP/s.
- Tensor cores (dense): fp16/bf16 ~989 TFLOP/s, tf32 ~494, fp8 ~1979. Ridge point fp16: 989 / 3.35 = ~295 FLOP/byte.
- Hopper features: **WGMMA** (warpgroup-level async MMA, operands from smem; `sm_90a` only), **TMA** (async tensor copies between global and shared memory, 1D-5D, issued by one thread, completion via mbarrier), **thread-block clusters** (up to 8 portable, 16 with an opt-in attribute; distributed shared memory; TMA multicast), `setmaxnreg` (shift registers between producer and consumer warpgroups), async barriers (`cuda::barrier`, mbarrier PTX).
- Rules of thumb: below ~295 FLOP/B a kernel is memory-bound, above compute-bound. Coalesce 32-byte sectors, use 16-byte vector accesses, pad or swizzle smem against bank conflicts (32 banks x 4 B).
- Compile for `sm_90a` (not plain `sm_90`) to use WGMMA/TMA. The Modal image sets `TORCH_CUDA_ARCH_LIST=9.0a`.
- Modal containers cannot lock GPU clocks (use `ncu --clock-control none`); `nvidia-smi` details of the actual run are saved in `candidates/<id>/logs/gpu_info.txt`.
- Detail: `./optk kb search "..."` over the Hopper Tuning Guide, the CUDA Best Practices Guide and the Colfax TMA / H100 matmul worklogs.
